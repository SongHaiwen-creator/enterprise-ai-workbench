# Feature 006 - Knowledge Base Management API

Status: Approved
Milestone: 2

## 1. Goal

Introduce the first Enterprise Knowledge Base capability by allowing authorized
Workspace members to create and manage Knowledge Base metadata through the
backend API.

This feature establishes the workspace-isolated persistence and authorization
foundation required by later Document Management and RAG features. It does not
ingest documents or perform retrieval.

## 2. Scope

This feature will:

- Add the `knowledge_bases` PostgreSQL table through a new Alembic migration.
- Add the Knowledge Base SQLAlchemy model, status enum, schemas, service layer,
  routes, and router registration.
- Allow active Workspace members to list and read Knowledge Bases in their
  Workspace.
- Allow active `knowledge_admin` and `system_admin` members to create, edit,
  disable, and re-enable Knowledge Bases in their Workspace.
- Persist the authenticated creator in `created_by`.
- Enforce Workspace status, Membership status, role, and resource scoping in the
  backend.
- Add PostgreSQL integration tests and regression verification.

No new runtime dependency is required.

## 3. Business Rules

### BR-001 - Workspace Ownership

A Knowledge Base belongs to exactly one Workspace and stores that Workspace ID.
Every query for a Knowledge Base must be scoped by both `workspace_id` and the
Knowledge Base ID where applicable.

### BR-002 - Read Access

Any authenticated User with an active Membership in an active Workspace may
list and read that Workspace's Knowledge Bases.

The list includes both active and disabled Knowledge Bases so their management
state remains visible. Disabled Knowledge Bases will be excluded from retrieval
when the RAG feature is implemented.

### BR-003 - Management Access

Creating or updating a Knowledge Base requires an active Membership whose role
is either:

- `knowledge_admin`
- `system_admin`

The `employee` and `agent_admin` roles cannot create or modify Knowledge Bases.

### BR-004 - Workspace State

Existing Workspace authorization rules apply. A missing Workspace returns 404.
A disabled Workspace, missing Membership, invited Membership, or disabled
Membership returns the existing Workspace access 403 response.

### BR-005 - Status

Supported Knowledge Base statuses are:

- `active`
- `disabled`

New Knowledge Bases default to `active`. Disabling is reversible through the
update endpoint. Hard deletion is not supported.

### BR-006 - Creator

`created_by` is always taken from the authenticated User. Clients cannot submit
or override it.

### BR-007 - Validation

- `name` is required, trimmed, and limited to 255 characters.
- `description` is optional, trimmed when provided, and limited to 5,000
  characters.
- A PATCH request must contain at least one supported field.
- Unknown request fields are rejected.
- Knowledge Base names are not required to be unique in the MVP.

## 4. Authorization Matrix

| Endpoint | Active member | Knowledge admin | System admin |
|---|---:|---:|---:|
| `GET /api/workspaces/{workspace_id}/knowledge-bases` | Yes | Yes | Yes |
| `GET /api/workspaces/{workspace_id}/knowledge-bases/{knowledge_base_id}` | Yes | Yes | Yes |
| `POST /api/workspaces/{workspace_id}/knowledge-bases` | No | Yes | Yes |
| `PATCH /api/workspaces/{workspace_id}/knowledge-bases/{knowledge_base_id}` | No | Yes | Yes |

`employee` and `agent_admin` are represented by "Active member" for mutation
decisions. Authentication and authorization are enforced by FastAPI backend
dependencies, not frontend visibility.

## 5. Database Contract

Table: `knowledge_bases`

| Field | Type | Rules |
|---|---|---|
| `id` | UUID | Primary key, generated by PostgreSQL |
| `workspace_id` | UUID | Required FK to `workspaces.id`, `ON DELETE RESTRICT` |
| `name` | VARCHAR(255) | Required |
| `description` | TEXT | Nullable |
| `status` | VARCHAR(32) | Required, `active` or `disabled`, default `active` |
| `created_by` | UUID | Required FK to `users.id`, `ON DELETE RESTRICT` |
| `created_at` | TIMESTAMPTZ | Required, database default current timestamp |
| `updated_at` | TIMESTAMPTZ | Required, database default current timestamp |

Indexes:

- `ix_knowledge_bases_workspace_id`
- `ix_knowledge_bases_created_by`

Constraints:

- Primary key on `id`.
- Foreign keys for `workspace_id` and `created_by`.
- Check constraint limiting `status` to `active` or `disabled`.

Migration requirements:

- Create a new revision `0003` with `down_revision = "0002"`.
- Do not modify revisions `0001` or `0002`.
- Upgrade creates only the Knowledge Base table and its indexes.
- Downgrade removes only the Knowledge Base table.

## 6. API / Data Contract

### 6.1 Create Knowledge Base

Endpoint:

`POST /api/workspaces/{workspace_id}/knowledge-bases`

Request:

```json
{
  "name": "Employee Policies",
  "description": "Approved policies for employee self-service"
}
```

Success: `201 Created`

The response uses `KnowledgeBaseResponse`.

### 6.2 List Knowledge Bases

Endpoint:

`GET /api/workspaces/{workspace_id}/knowledge-bases`

Success: `200 OK`

Returns all Knowledge Bases belonging to the route Workspace, ordered by
`name`, then `id`. An empty Workspace returns an empty list.

### 6.3 Get Knowledge Base

Endpoint:

`GET /api/workspaces/{workspace_id}/knowledge-bases/{knowledge_base_id}`

Success: `200 OK`

If the Knowledge Base does not exist in the route Workspace, return 404 with:

```json
{
  "detail": "Knowledge base not found"
}
```

### 6.4 Update Knowledge Base

Endpoint:

`PATCH /api/workspaces/{workspace_id}/knowledge-bases/{knowledge_base_id}`

Request fields are optional individually, but at least one must be supplied:

```json
{
  "name": "Global Employee Policies",
  "description": "Current approved employee policies",
  "status": "disabled"
}
```

Success: `200 OK`

The response uses `KnowledgeBaseResponse`.

### 6.5 Response Schema

`KnowledgeBaseResponse` fields:

```json
{
  "id": "knowledge-base-uuid",
  "workspace_id": "workspace-uuid",
  "name": "Employee Policies",
  "description": "Approved policies for employee self-service",
  "status": "active",
  "created_by": "user-uuid",
  "created_at": "2026-09-15T10:00:00Z",
  "updated_at": "2026-09-15T10:00:00Z"
}
```

## 7. Error Behavior

### 401 Unauthorized

Missing, invalid, malformed, or expired Bearer credentials retain the existing
authentication response and `WWW-Authenticate` behavior.

### 403 Forbidden

Existing Workspace access failures retain:

```json
{
  "detail": "Not authorized for this workspace"
}
```

A mutation attempted without an allowed role returns:

```json
{
  "detail": "Knowledge administrator role required"
}
```

### 404 Not Found

- Missing route Workspace: `Workspace not found`.
- Missing Knowledge Base, including an ID belonging to another Workspace:
  `Knowledge base not found`.

### 422 Unprocessable Entity

Used for invalid UUIDs, empty or oversized fields, invalid status values,
unknown fields, an empty PATCH body, and other request-schema validation
failures.

Unexpected database details must not be exposed to clients.

## 8. Application Structure

Request flow:

```text
HTTP Request
-> Current User dependency
-> Active Workspace Membership dependency
-> Knowledge Administrator dependency for mutations
-> Route
-> Knowledge Base service
-> SQLAlchemy
-> PostgreSQL
```

Routes handle HTTP contracts, services handle persistence behavior, and models
and database constraints enforce stored-data invariants. No repository layer is
introduced.

## 9. Acceptance Criteria

### AC-001 - Migration

Alembic upgrades from revision `0002` to `0003`, creates the specified table,
indexes, foreign keys, and status constraint, and can downgrade back to `0002`
without modifying existing tables.

### AC-002 - Create

An active `knowledge_admin` or `system_admin` can create a Knowledge Base in an
active Workspace. The Workspace, creator, default status, and timestamps are
persisted and returned.

### AC-003 - Read

Any active Workspace member can list and retrieve Knowledge Bases belonging to
that Workspace. Results include active and disabled records and are ordered by
name and ID.

### AC-004 - Update and Disable

An active `knowledge_admin` or `system_admin` can update the name, description,
or status of a Knowledge Base and the changes persist.

### AC-005 - Role Enforcement

An active `employee` or `agent_admin` receives 403 when attempting to create or
update a Knowledge Base.

### AC-006 - Membership and Workspace State

Non-members, invited members, disabled members, and members of disabled
Workspaces cannot access Knowledge Base routes.

### AC-007 - Workspace Isolation

A caller cannot read or update a Knowledge Base from another Workspace by
placing its ID under an authorized Workspace route.

### AC-008 - Validation

Invalid create and update payloads return 422 and do not persist changes.

### AC-009 - Existing Behavior

Authentication, Workspace and Membership APIs, database migrations, health,
CORS, and frontend behavior continue to pass their existing verification.

## 10. Test Requirements

PostgreSQL integration tests must cover:

- Migration `0002 -> 0003`, Alembic head, schema constraints, and downgrade.
- Authentication required on all Knowledge Base routes.
- Successful creation by `knowledge_admin` and `system_admin`.
- Creation denial for `employee` and `agent_admin`.
- Persisted `workspace_id`, `created_by`, default status, and timestamps.
- Ordered list and empty-list behavior.
- Reading active and disabled Knowledge Bases.
- Successful name, description, disable, and re-enable updates.
- Empty PATCH and invalid payload validation.
- Missing Workspace and Knowledge Base behavior.
- Cross-Workspace read and update isolation.
- Invited and disabled Membership denial.
- Disabled Workspace denial.
- Existing authentication and Workspace/Membership regressions.

Verification must include:

- Feature-specific PostgreSQL integration tests.
- Full backend `pytest` suite against PostgreSQL.
- Backend Ruff checks.
- Frontend unit tests, lint, and production build.
- `git diff --check`.

SQLite must not replace PostgreSQL integration tests. Required tests must not be
skipped when the feature is reported as PR-ready.

## 12. Out of Scope

- Frontend Knowledge Base management UI.
- Document records, upload, storage, parsing, versioning, or processing status.
- Chunking, embeddings, pgvector, retrieval, LLM generation, or citations.
- OCR, complex tables, images, audio, or video ingestion.
- Knowledge Base deletion or bulk operations.
- Fine-grained document or department permissions.
- Custom roles or changes to existing Workspace/Membership role values.
- Public registration, invitations, or user-directory search.
- Agents, tools, workflows, approvals, execution logs, or evaluation.
